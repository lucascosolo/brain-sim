# P2-E4 implementation review: bugs lens

Fresh reviewer given only the files (driver at commit d404332, contract frozen at cd17cde); each finding checked by a separate refuter. Run 2026-10-10. Recorded verbatim.

## Verdict

The gated simulation path looks correct. I checked the forward-store identity, repetition-1 identity, the live rec projection, the slot windows, block_criteria, hab_criteria/_hab_fast, the schedule rules and JSON serialisation of the gated record. Off-by-one indexing, stream keys and deep-copy aliasing are clean. All validity checks pass on TINY seed 92 and on the full config, seed 91, up to M=1,000, with a replay mismatch of 0 at M=1,000 (seed 90). One blocker: `verdict()` cannot run on the real results file, so it cannot produce the gated label. The predictions/guard chain also has gaps that let a code or contract change between exploration and gating go undetected. It also leaves out numbers the contract says must be committed. Two reported numbers are wrong: `offset_settled`, and the matched-episodes comparison of the writes-during-probes arm. Per-slot data is not saved, so any aggregation bug found later forces a re-run. All of these sit in the plant2 tree, so they must be fixed before exploration on seeds 42-43.

## Findings

### F1 [blocker] verdict() crashes on the real results file and would pick up P2-E2/P2-E3 gated records

- where: plant2/experiments/p2_e4_online.py:1000-1002
- evidence: Line 1000 reads `gated = [r for r in recs if r["gated"] and r["kind"] == "kill_test_seed"]` with no experiment filter. I ran `e4.verdict(e4.load_records(), results_path=<cache>)` (read-only) and got `KeyError 'gated'`: P2-E1 records, calibration points and power_reference lack that key. I appended five fake P2-E4 gated records: same KeyError. Restricting to records that have 'gated' gives `SystemExit verdict needs exactly the gated seeds (16..20); have [6, 7, ..., 20]`, because P2-E2 (6-10) and P2-E3 (11-15) gated kill_test_seed records match. So the verdict label, a gated output, cannot be produced. Fixing it after gating would change the plant2 tree the gated runs were pinned to. No test calls verdict() on a realistic file.
- fix: Filter with `r.get("experiment") == "P2-E4" and r.get("kind") == "kill_test_seed" and r.get("gated") and r.get("contract_digest") == DIGEST`. Keep the first record per seed (the contract says re-runs keep the first records). Add a unit test that runs verdict() on the committed bench/results/plant2.jsonl plus five synthetic P2-E4 gated records.
- independent verifier: **confirmed** (severity should be blocker): Reproduced read-only (output to ~/.cache/brain-sim/review/p2e4-impl/verify-bugs/f1.jsonl). On the real bench/results/plant2.jsonl (71 records), verdict() raises KeyError 'gated'. The file's first records are P2-E1 records, which have no 'gated' key, and line 1000 reads r["gated"] before any experiment test. The same KeyError occurs with five fake P2-E4 gated records added. Restricting to records that have 'gated' gives SystemExit 'have [6..20]', because the P2-E2 (6-10) and P2-E3 (11-15) kill_test_seed records carry gated=True. So the verdict label can never be produced from the frozen tree. Fixing it after gating means post-hoc code for the label. No test calls verdict(). The fix is right: filter on experiment == 'P2-E4', kind, gated and DIGEST, keep the first record per seed, and add a test on the committed file plus synthetic records.

### F2 [major] predictions() never checks that exploration ran on the code being gated; duplicate exploration records are double-counted

- where: plant2/experiments/p2_e4_online.py:1028, 1121
- evidence: The exploration filter is `r.get("experiment") == "P2-E4" and r["kind"] == "exploration_seed" and r["contract_digest"] == DIGEST`. DIGEST hashes only the CONTRACT constants, so a driver change after exploration (bug fix, scoring change) leaves it unchanged. The guard (1121) compares only the predictions record's plant2_tree with HEAD's. A tree changed between exploration and predict therefore passes every check, which is exactly the 'tree may not change between exploration and gating' rule. Also, run_seed appends the exploration_seed record before the reported arms (911-914). If a reported arm crashes (e.g. OOM) and `explore --seeds 42` is re-run, seed 42 is pooled twice: n doubles in the Beta posterior, and the bootstrap pool duplicates 50 items.
- fix: In predictions(), require every pooled record to have `r["git"]["plant2_tree"] == record.git_state()["plant2_tree"]` and `not r["git"]["plant2_dirty"]`, and raise otherwise. Keep one (the first) record per seed, and require the seed set to equal EXPLORE_SEEDS. Store the exploration records' trees in the power_predictions record. Also refuse to predict when plant2 is dirty.
- independent verifier: **confirmed** (severity should be major): Line 1028 filters only on experiment, kind and DIGEST, and DIGEST = record.digest(CONTRACT) covers constants only. There is no check of the records' git.plant2_tree or plant2_dirty, no de-duplication and no restriction to EXPLORE_SEEDS. run_seed appends the exploration_seed record (line 911) before run_reported (line 914), and no command runs the reported arms alone. A crash in the reported arms followed by a re-run of 'explore --seeds 42' therefore appends a second, identical record. Seed 42 is then pooled twice: n goes from 400 to 600 in the Beta posterior, and seed 42 gets twice seed 43's weight in the item bootstrap. 'explore --seeds 90' is also allowed by the CLI and would be pooled. The append-only file means only a code change could undo this once exploration has started. One caveat: the contract's guard wording (predictions tree == HEAD tree) is met. The missing exploration-tree check is a gap in enforcing the review rule, not a contract violation, and the duplicate would be visible in exploration_seeds. The fix is right: one record per seed, seed set == EXPLORE_SEEDS, every record's plant2_tree == the current tree and not dirty.

### F3 [major] The guard does not detect a committed change to the frozen contract document

- where: plant2/experiments/p2_e4_online.py:1113, 1121
- evidence: The only check on the document is `git diff --quiet HEAD -- docs/plant2/P2-E4-online-memory.md`, which catches only uncommitted edits. The 'contract digest' compared (p["contract_digest"] != DIGEST) is the hash of the code's CONTRACT dict, which the plant2 tree hash already covers. So an edit to the gated criteria committed after cd17cde passes the guard. The contract asks the guard to check that 'the tree hash and contract digest match'. The power_reference record stores contract_sha256 of the document, but the predictions record has no document hash and the guard checks none. The document will legitimately grow when predictions are appended, so a plain equality check to cd17cde would not work.
- fix: In guard(), require `git show cd17cde:docs/plant2/P2-E4-online-memory.md` to be a byte prefix of `git show HEAD:docs/plant2/P2-E4-online-memory.md` (append-only), and require that cd17cde is an ancestor of HEAD (`git merge-base --is-ancestor`). Record the HEAD document's sha256 in each kill_test_seed record.
- independent verifier: **partly** (severity should be minor): Factually true: the guard (line 1113) catches only uncommitted edits to the document. The compared 'contract_digest' is the CONTRACT-dict digest, which the plant2 tree hash already covers. But that is the codebase's convention for 'contract digest' (P2-E2 and P2-E3 records use record.digest of the config, p2_e3_completion.py:38). The contract's guard bullet ('tree hash and contract digest match') is satisfied in that reading. A committed doc edit cannot change any gated number, since the code computes them, and it would show in git history. So this is hardening, not a defect. The proposed fix is also unsafe. The contract says real-driver predictions are 'appended below' the red-team numbers, inside 'Predictions before implementation' (line 489), which is followed by the 'Decision' and 'Files' sections. A legitimate edit there would fail a byte-prefix test. Better: require that `git diff cd17cde HEAD -- docs/plant2/P2-E4-online-memory.md` contains no removed or changed lines (additions only), and that cd17cde is an ancestor of HEAD.

### F4 [major] predictions() leaves out committed items the contract requires (logit shift, per-label probabilities)

- where: plant2/experiments/p2_e4_online.py:1066-1079
- evidence: The shift is searched only `if p45 > 0.8` and only for delta >= 0. It holds O4-O5 fixed at the bootstrap value, though the contract asks for 'one common logit shift of all rates'. On synthetic exploration records with M=1000 habituation items at a per-cue 'both' rate of 0.77 (the contract's own M=1000 prediction), predictions() gave habituation_5seeds['1000'] both=0.0 and logit_shift_for_p08=None. The committed record would therefore lack the number the contract lists. When P(PASS) at the mean rates already exceeds 0.8, the loop returns 0.0 rather than the threshold. Per-label probabilities for HABITUATION FAIL vs NOT ESTIMABLE and RECOVERY FAIL vs NOT ESTIMABLE are not computed. The P(PASS) interval also ignores bootstrap uncertainty in p45. This code is frozen after exploration, so it cannot be completed later.
- fix: Make the shift act on every per-cue rate. For O4-O5, shift each bootstrapped item's late/recovery/collateral outcomes through a parametric model, e.g. power.p2e4_o4_o5 at the shifted control-copy 'both' rate. Search delta in [-6, 6] for the smallest delta with P(PASS) >= 0.8, and report the shifted rates. In the bootstrap, tally O4 fail with/without >= 25 eligible and O5 fail with p0 >= or < 0.8 (as labels() would). Draw p45 per posterior draw so the interval carries both uncertainties.
- independent verifier: **confirmed** (severity should be major): Reproduced with predictions() on two synthetic exploration records (output to the cache). Rates were 0.95 for O1-O3, with habituation per-cue 'both' at 0.96 for M=500 and 0.77 for M=1000. Result: habituation_5seeds['1000'] = {O4 0.0, O5 0.0, both 0.0}, logit_shift_for_p08=None, P(PASS) [0,0]. The record has no key for HABITUATION FAIL vs NOT ESTIMABLE or RECOVERY FAIL vs NOT ESTIMABLE. From the code: the shift acts on O1-O3 only, holds p45 fixed, is attempted only when p45 > 0.8, and starts at delta=0, so it returns 0.0 (or 0.05) when the mean rates already pass. The interval p_pass = p_draws * p45 (line 1065) carries no bootstrap uncertainty in p45. The contract's own prediction (O4 not estimable at M=1000, P(PASS) < 0.05) means the committed record will almost certainly lack the listed 'one common logit shift of all rates' and the per-label probabilities (contract lines 440-443). Severity: the omitted predictions are committed, predeclared items and the interval is too narrow, so major. The missing numbers could in principle be computed by a script outside plant2, which slightly softens this.

### F5 [major] offset_settled is measured after twin B's 60 s of cueing, not after the settle

- where: plant2/experiments/p2_e4_online.py:935-936
- evidence: In `dict(twin_A=A, twin_B=twin_B(B, main, M), reference=..., offset_settled=float(B.mem.vbar.mean() - ...))`, keyword arguments are evaluated left to right, so twin_B() first runs the 200 ms lead-in plus 200 cues x 300 ms on B. Only then is B's vbar read. The contract's operating-point row wants 'block offset minus twin A's settled offset'. Measured on TINY (offset_settled.py), after settle vs the value recorded: seed 93 M=120 1.246 vs 2.194 mV, M=200 1.997 vs 3.437; seed 94 1.239 vs 2.270, 1.933 vs 3.483. At the full config 60 s is 6 accommodation time constants, so the recorded value is the cueing operating point.
- fix: Read `offset_settled = float(B.mem.vbar.mean() - float(B.mem.v_rest))` before calling twin_B (or return it from twin_A right after settle_drift). Optionally also record B's offset after the cue run under a separate key.
- independent verifier: **confirmed** (severity should be major): Reproduced on TINY, seed 93, M=120 (f5_offset.py in the cache). B's offset right after settle_drift is 1.246 mV. The value the driver's construction records is 2.194 mV, read after twin_B. The online block mean is 3.872 mV. These match the reviewer's numbers. Keyword arguments are evaluated left to right, and twin_B (lines 721-748) mutates B through a 200 ms lead-in plus 200 x 300 ms of cueing. settle_drift (p2_e3_completion.py:88-98) returns only the drift deltas, so twin A's settled offset is recorded nowhere else. The contract's operating-point row ('block offset minus twin A's settled offset', predicted ~3.7 mV settled) would therefore get the cueing operating point. Fix: read the offset before calling twin_B.

### F6 [major] Writes-during-probes 'matched plateau episodes' comparison is always empty (NaN)

- where: plant2/experiments/p2_e4_online.py:837-842
- evidence: `rolling_main_matched_episodes=rolling_summary(main_final, max(M + 1, episodes - 70), episodes + 70)` keeps only `d["block"] is None` slots. With episodes = 1000 + 200 + writes ≈ 1,370, the window [~1300, ~1440] lies wholly inside stress block 1500 (steps 1261-1500). Seeds 90-99, real schedule (wps_window.py): planned writes 164-177, episodes 1364-1377, rolling half-cue slots in the window = 0 on every seed. So n=0 and C1/joint are NaN, and the contract's predeclared 'matched plateau episodes (about 1,370)' comparison never happens. TINY does not show this (n=7) because its stress block sits elsewhere.
- fix: Compare against all main-line half-cue slots in the window, including stress-block recent/uniform cues with their ages, or use stress block 1500's recent cues as the matched-episode reference. Record n and the realised ages next to each rate.
- independent verifier: **confirmed** (severity should be major): Recomputed from schedules only (sched_checks.py, seeds 90-99). WPS writes (non-blank rolling slots in steps 1001-1200) are 164-177, giving episodes 1364-1377 and windows such as (1299,1439) to (1307,1447). Stress block 1500 spans steps 1261-1500, so rolling_summary(..., block is None) has n=0 on every seed and C1 and joint are NaN. For the window to reach a rolling step, writes would have to be below 131, about 8 SD under the mean of 170. The predeclared 'matched plateau episodes (about 1,370)' comparison will be empty on every gated seed. TINY does not reveal this, and the tree is frozen once exploration starts. Major is borderline (n=0 is recorded, so the number is missing rather than misleading), but it is a predeclared comparison lost on every seed. Fix: score every main-line half cue in the window, including stress-block recent and uniform cues, and record n and the ages.

### F7 [major] Per-slot outcomes are not persisted, so gated seeds cannot be re-analysed without a re-run

- where: plant2/experiments/p2_e4_online.py:866-915 (run_seed), 559-618 (habituation)
- evidence: main.log (per-cue recall, spurious, missing, intrusions, joint, age, offset, rec_v for all 1,000 steps), the per-step tuples of each habituation copy (recall, joint), and the twin B pairs are reduced to aggregates. The TINY exploration_seed record is 9.5 KB. Any aggregation error found after the gated runs (the P2-E3 class of bug) costs a full re-run or an INVALID verdict. Several contract-reported analyses also cannot be computed from the records: 'cued minus blank by age, age 0 separately', per-repetition recall (only 'both' is kept), McNemar on 'L >= 8' detail per item.
- fix: Write main.log for steps 1..1000 and each copy's per-step (s, t, both, recall, joint, missing, intrusions) to `record.cache_dir("p2_e4")/seed{S}_{kind}.npz` (or jsonl), and store its path and sha256 in the kill_test_seed record. Alternatively embed the 480 gated block slots (~100 KB) in the record.
- independent verifier: **partly** (severity should be minor): True that main.log, the per-step outcomes of each habituation copy and twin B's pairs are reduced to aggregates. Persisting them would let an aggregation bug be re-analysed outside the plant2 tree. But the contract does not require raw logs, so this is a robustness recommendation, not a defect. Of the listed analyses, McNemar on 'L >= 8' is refuted. hab_criteria computes it (lines 646-647), and per-item L_rep and L_ctl are stored in loads[M]['hab_items'] in the gated record, so it can be recomputed. Per-repetition recall is genuinely missing: items keep only per_rep_both, while the contract asks for 'per-repetition recall and "both"'. 'Cued minus blank by age' is also missing (it duplicates F8c). Fix: add per_rep_recall to the hab items and optionally save the per-slot logs to cache_dir with a sha256 in the record.

### F8 [minor] Several contract-reported items are missing or mislabelled

(d) Validity 6 digests are not taken around reported-arm copies (twin A/B, OOD, WPS), so a reported arm cannot be invalidated as the contract allows.
- fix: Score the live rec log of twin A with build_cues windows and report joint_live - joint_replay. Record rec.v.mean() at slot onset inside sham_step. Add a per-age (0, 1-20) cued vs blank recall table to block_criteria. Wrap each reported-arm copy in state_digest before/after on its source snapshot.
- independent verifier: **confirmed** (severity should be minor): (a) twin_A records replay_only, live_only and replay_spikes counts (line 714) but never the 'effect on the joint' the contract asks for (line 277). The effect is trivially zero when the mismatch is 0, which the TINY test asserts. (b) hab_copy records rec_v_end, which is e.rec.v.mean() after the final post-gap (line 590), not rec v at slot onset as the contract asks (line 462, SHAM-1). (c) block_criteria has no per-age cued-vs-blank table. Only the blank age-0 leak_A is computed, and retention_by_age lumps ages 0-20. (d) twin_A, ood_arm and wps_arm deep-copy snapshots with no state_digest before and after, although the contract says digests are taken around 'each copy' and that a reported arm can be invalidated (line 351). ### F9 [nit] Pseudo-targets ignore the 'minus already-targeted' rule and the blank age-0 share

- where: plant2/experiments/p2_e4_online.py:129-136
- evidence: `slot["pseudo"] = (int(r.choice(el)), ...)` draws from unreserved ages 0-20 without excluding items already targeted in the block. Over seeds 90-99 (pseudo_overlap.py) 52 of 400 pseudo-targets (13.0%) had been cued or blank-targeted earlier in the block. 5.8% are at age 0, against 25% of the blanks the baseline is compared with. At the full config, seed 91, all leak values were 0.0 (L_A, L_C, B_A, B_C, age-0 blanks), so there is no practical effect now.
- fix: Draw pseudo-targets from the blank eligible set minus `used`, and match the age-0 share (e.g. at age 0 in the novel slots of the odd sub-blocks), or compute the baselines per age stratum.
- independent verifier: **partly** (severity should be nit): The numbers reproduce exactly from schedules: 400 pseudo-targets on seeds 90-99, 52 (13.0%) already targeted earlier in the block, and 23 (5.75%) at age 0. But it is ambiguous whether the 'minus every item already targeted' rule binds pseudo-targets. The contract applies it to each 'targeted slot', while pseudo-targets are 'never cued'. The code's 0-20 eligible set does follow the sampler table ('recent and blank: unreserved items of age 0-20'). The age-0 share mismatch with the blanks (5 of 20) is real but not required by the text. The reviewer reports all leak values at 0.0 on the full config, so there is no practical effect.

### F10 [nit] run_seed stamps the real contract digest on any config

- where: plant2/experiments/p2_e4_online.py:908
- evidence: `contract_digest=DIGEST` is written whatever `c` is. My TINY run (tiny_92.jsonl) carries the real DIGEST, so a TINY or debug run written to the default results path would pass predictions()' only filter and be pooled as exploration.
- fix: Use `contract_digest=record.digest(c)`. Have explore/run refuse any c other than CONTRACT.
- independent verifier: **confirmed** (severity should be nit): Lines 908 and 920 stamp contract_digest=DIGEST whatever c is. A TINY run written to the default path would pass predictions()' filter. It would then raise KeyError on r['loads']['500'] (TINY loads are '120' and '200') rather than be silently pooled, which makes predict permanently fail on the append-only file. Both cases need a programmatic call with the default path, since the CLI always uses CONTRACT. Fix: contract_digest=record.digest(c), and refuse c != CONTRACT on the default results path.

### F11 [nit] NaN written into JSONL records

- where: plant2/experiments/p2_e4_online.py:439-440 (frac)
- evidence: frac([]) returns NaN, and json.dumps emits the non-standard token NaN. In the TINY records: per_kind.uniform_cohort500 at the first gate load (always n=0 at M=500 in the real config), recovery_among_habituated, retention bins and M250_rolling. Python reads NaN back, but strict JSON tools (jq, JS) reject it.
- fix: Return None for empty populations in reported fields. The gated vector already turns NaN into False, which is the intended fail.
- independent verifier: **confirmed** (severity should be nit): frac([]) returns float('nan'), and record.append uses json.dumps with the default allow_nan, which emits the token NaN. per_kind.uniform_cohort500 at M=500 always has n=0. Python's json.loads reads NaN back, so guard, predict and verdict are unaffected. The gated vector compares NaN >= 0.9, giving False, which is the intended fail. Only strict JSON tools are affected.

### F12 [nit] twin_A's spike-set replay comparison is memory-heavy; parallel gated seeds risk OOM in the reported arms

- where: plant2/experiments/p2_e4_online.py:709-712, 293-294
- evidence: Full config, seed 90, M=1000 main-line twin A: 660,198 rec spikes, RSS 297 MB before, 783 MB peak after (≈380 B per spike from the trace list, the rp/live sets and _rec_log). The duty arm (predicted store collapse) and the novel-duty twin may fire several-fold more. The machine has 15 GB and no swap, and the guard docstring anticipates parallel gated seeds.
- fix: Log live rec spikes as per-tick int arrays and compare per tick with the replay (or count differences with np.setdiff1d on t*m+j int64 keys). Do not build Python tuple sets.
- independent verifier: **confirmed** (severity should be nit): twin_A builds Python tuple lists and sets for every rec spike: the _rec_log extend (line 294), the replay trace and the rp/live sets (lines 709-712). readout.py:25 documents the trace as '(tests only)'. The machine has 4 cores, 15 GB RAM and no swap. With the reviewer's ~0.5 GB per twin A, and even a several-fold larger duty-arm twin, 4 parallel seeds stay well below 15 GB, so OOM is unlikely. If it happened, it would hit the reported arms after kill_test_seed is appended, and run-once would block re-running them. Fix: compare per tick with integer keys (t*m+j, np.setdiff1d).

### F13 [nit] Run-once enforcement is computed once per invocation

- where: plant2/experiments/p2_e4_online.py:1152-1158
- evidence: `done = guard(load_records())` is computed before the loop, so `run --seeds 16 16` runs seed 16 twice. Two concurrent processes for the same seed both pass. load_records() can also read a half-appended line from a concurrent writer and crash with JSONDecodeError at start-up.
- fix: De-duplicate a.seeds. Re-read the records and re-check done immediately before each seed (or take an exclusive lock file per seed under ~/.cache/brain-sim). Skip unparsable trailing lines when reading.
- independent verifier: **confirmed** (severity should be nit): done = guard(load_records()) is computed once (line 1152) and never updated in the loop, so 'run --seeds 16 16' runs seed 16 twice, and two concurrent processes both pass. A second record would make verdict() fail its exact-seed check. load_records() has no handling for an unparsable line. Each case needs operator error or a rare read during a concurrent append, and the start-up failure is harmless. Fix: de-duplicate a.seeds, re-check done per seed (or use a lock file in ~/.cache), and tolerate a torn trailing line.
